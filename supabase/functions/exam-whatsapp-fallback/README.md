# Independent WhatsApp fallback

It preserves original bytes in private Supabase Storage and sends the same PDF to the configured existing group only when the shared primary grace/progress/stall policy permits takeover. It does not depend on n8n, Drive or AI extraction to send. Its caption and attachment filename now use the same presentation function as the primary flow, with persisted, evidenced fields and explicit human corrections. Missing fields stay missing; original filenames never stand in for a patient identity. Drive/processing remain honestly pending.

This covers n8n/Drive failure while Chatwoot remains reachable. Chatwoot and its WhatsApp bridge currently share the n8n VPS; this is not a fallback for total loss of that VPS or WhatsApp connectivity. That requires a separately hosted transport. No automatic provider switch can safely re-send an uncertain message without reconciliation.

Runtime: Supabase Edge Function invoked every minute by Supabase Cron. One fenced run (100s maximum) and up to six queued origins per run; newest pages are checked every run while older pages resume separately. Discovery commits to a durable source queue before its cursor advances. Retries back off up to 15 minutes without dropping the source, so repeated failures cannot monopolize every run. Receipt reconciliation has its own shared eight-second budget. Scope is one explicitly configured individual conversation. Every source is revalidated against inbox, account, sender allowlist, source ID and cutoff. This is not proof of all conversations or all WhatsApp traffic.

Required secrets (never commit values):

- `EXAM_FALLBACK_TRIGGER_KEY`: random dedicated trigger key; POST only, cannot choose destination or upload payload. The same key lives in Vault as `exam_whatsapp_fallback_trigger_key`.
- `EXAM_FALLBACK_CHATWOOT_API_TOKEN`: authorized user API identity limited to the intended account/inbox where supported. AgentBot tokens cannot list messages and therefore cannot operate this collector or reconcile its receipts. Preflight tests the actual read endpoints as well as the source identity and group JID.
- `EXAM_FALLBACK_CONFIG`: JSON with `chatwootBaseUrl`, `documentBaseUrl`, `authorizedSenders`, optional `allowedAttachmentOrigins`, `allowBrazilLegacyMobileAlias`. Configuration is server-owned.
- Standard Supabase backend secrets are consumed by the shared privileged-key selector.

Migration 44 creates disabled configuration. Configure exact source account/conversation and received_from only after reviewing the authorized scope; the existing exam configuration owns the group destination. Do not silently set a historical cutoff or send the old backlog. An enabled flag alone is not a verified deployment. Call `{action:"preflight"}` first with the trigger key; it reads provider conversations without dispatching. Activating requires meaningful offline tests, review of exact SQL against production, and an authorized synthetic provider test. Credentials, cron, configuration and real delivery are separate checkpoints.

Storage writes are immutable (`upsert:false`); even a 409 requires full hash/size readback. Source and byte canonicalization are shared with the primary flow. Group delivery uses the same task. A one-shot dispatch fence marks it uncertain before POST. Any response loss is reconciled through GET; never POST again because a response or receipt was lost. Active primary reservations are not stolen; this can delay takeover when a prior submission is uncertain. Do not misrepresent that case as a guaranteed two-minute delivery.

The presentation path requires migration `20261105000102_exam_fallback_presentation_fence.sql`: claim → `prepare_exam_fallback_group_dispatch` → provider preflight → `begin_exam_fallback_group_dispatch_v2` → one POST. Prepare refreshes fields after byte verification; begin checks the same presentation revision immediately before POST. Human edits during preflight defer the old caption without sending or recording an operational failure. Legacy uncertain/submitted tasks still reconcile without another POST. All post-grant failures, including a definitive HTTP 4xx rejection, remain `uncertain` under the shared SQL contract and require reconciliation/review.

`exam-presentation.generated.mjs` is generated from `scripts/exames/notification-presentation.mjs`; regenerate it with `node supabase/functions/exam-whatsapp-fallback/generate-exam-presentation.mjs`. The transport tests verify exact generated source and output parity, including human nulls, incomplete fields, assigned veterinarian, filename and short link. The generator is a local build utility; runtime imports only the generated module. The central presentation source remains authoritative.

Known Chatwoot receipt IDs are read using `before=external_id+1`, then checked against the document, delivery, hash and PDF attachment. If the POST response was lost and no receipt ID is known, each reconciliation checks at most three recent message pages. Without a complete unique match, the task remains `uncertain` and requires review; this version does not persist a separate historical reconciliation cursor and does not resend automatically.

Once the group has the PDF, later primary processing must preserve the existing sent task. The fallback does not mark Drive completed, fabricate extraction, attach to a patient, or send a second notification on return. Storage-to-Drive promotion is a separate follow-up for completing the primary pipeline, not a prerequisite for fallback delivery.

Install `supabase/operations/exam-whatsapp-fallback-scheduler.sql` after migration 44. It installs one inactive cron job. Cron signs the fixed run body with HMAC instead of putting a permanent Bearer key into the readable pg_net request queue. The Edge verifies the signature and atomically consumes the issued nonce (120-second expiry). Operator preflight uses the dedicated Bearer key directly, outside pg_net. `set_exam_fallback_schedule(false)` pauses only this fallback and preserves its queue, cutoff, originals and receipts. Reinstallation leaves the cron job inactive; never interpret a successful cron enqueue as proof of PDF delivery.

Verification: `node --test supabase/tests/whatsapp-fallback-*.test.mjs supabase/tests/exam-whatsapp-fallback.test.mjs` covers the collector, transport, runner, SQL contract, authentication and scheduler. SQL tests use PGlite; scheduler extensions are explicitly stubbed. HMAC uses real WebCrypto. These checks do not replace a real provider preflight and controlled delivery receipt. No independent outage alert, whole-VPS continuity or Storage-to-Drive promotion is implemented by this change.
